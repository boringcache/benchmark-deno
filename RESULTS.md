# Deno release Rust cache proof result

Run date: 2026-07-27  
Proof run: [GitHub Actions run 30303520865](https://github.com/boringcache/benchmark-deno/actions/runs/30303520865)  
Pinned pair: `0c965f5e` -> `c3ea533f` (one Rust file and one TypeScript file changed)

## Decision result

| Strategy | Restore/setup | Build | End-to-end | Seed storage | Rust cache result |
|---|---:|---:|---:|---:|---:|
| GitHub Actions Cargo + `target/` archives | 64s | 1,681s | 1,745s | 2.77 GiB | n/a |
| BoringCache Cargo registry + remote sccache | 25s | 2,226s | 2,251s | 2.07 GiB | 2,957 hits / 59 misses (98%) |

BoringCache stored 749,887,055 fewer bytes, a 25.3% reduction, but was 506
seconds (29.0%) slower on the rolling restore-plus-build path. This result does
not support replacing Deno's release `target/` archive with sccache alone.

The useful technical result is the combination of a 98% Rust cache hit rate
and a slower overall build. Deno's release surface is dominated after
compilation by ThinLTO, linking, and snapshot work. Restoring `target/` retains
that state; compiler-object caching does not.

## Storage correction

The comparison artifact generated by this run records zero bytes for the
Actions seed because the first version of the measurement helper accepted only
`GITHUB_TOKEN` while the workflow exported `GH_TOKEN`, and it treated GitHub's
exact cache-key API parameter as a prefix filter.

The two saved entries remain visible through GitHub's cache API and total
2,969,196,079 bytes:

- target archive: 2,815,113,001 bytes
- Cargo archive: 154,083,078 bytes

The helper now performs client-side prefix matching, accepts either token name,
and fails the workflow rather than publishing a zero measurement. A live check
against this run returns the exact total above.

## Next proof

The next experiment should not repeat the same pure-sccache lane. Test these in
order:

1. BoringCache sccache plus a narrow archive of
   `target/release/lto-cache`. Deno caps this directory at 700 MB, and it targets
   the measured bottleneck without restoring the whole target tree.
2. The high-frequency Linux debug build used on ordinary pull requests. It has
   much less release-link work and is a better surface for compiler caching.

Only propose a production migration after one of those rolling paths beats the
existing Actions restore-plus-build time in repeated runs.
